3. How will you authenticate?

The hub rejects every command except Login until a valid pair-id authenticates the session. Pick the path that matches your hub's current state — read this before connecting, because once this page grabs the BLE link, the QuietCool Smart Control app can't talk to the hub at the same time.

Once the QuietCool Smart Control app on Android or iOS pairs with a hub, the factory test ID stops working and the real pair-id isn't user-visible. This path side-steps that by putting the hub into pair mode so we can register a fresh ID.

Pick whichever is easier for you — both end with the hub advertising as pairable for ~tens of seconds:

Method A — physical button
  1. Find the Pair button (KEY2) on the hub. It's the same button used during initial setup.
  2. Press and hold it for 3 or more seconds, then release. LED4 (the pair LED) will change to indicate the hub is pairable.
  3. Come back here and press the Connect & flash button in step 6 below — quickly, the window is short.
Method B — Smart Control app
  1. On a phone with the QuietCool Smart Control app (available on Android and iOS — it needn't be the device running this installer), tap your hub, then tap Pair Mode.
  2. Wait until the app confirms pair mode is active.
  3. Force-close the OEM app (swipe it away in the recents view). The hub only allows one BLE central at a time — leaving the app open will block this page from connecting.
  4. Come back here and press the Connect & flash button in step 6 below.

When you press Connect & flash, this wizard will register a fresh random pair-id with the hub and save it in this browser so you can retry without re-running pair mode if anything goes wrong.

A factory-fresh hub accepts the OEM's built-in test pair-id with no button press — just keep the default below. This also works if you saved a pair-id from a previous run of this wizard in this browser.

Default 1234567dsad8wqw9asasd is the OEM's factory test ID — it stops working the first time the QuietCool Smart Control app on Android or iOS pairs with the hub.

Already running the ESPHome firmware?

If your hub is already running the ESPHome firmware, use this section to flash any compatible firmware URL onto it: the verified OEM stock V4.1 to roll back, a custom build hosted somewhere, or an alternative ESPHome image. It uses the device's built-in POST /api/flash_url endpoint over plain HTTP, no Bluetooth required. The OEM preset supplies the exact verified URL+MD5 pair that tells the device to confirm the foreign stock slot and preserve OEM NVS state during final cleanup.

The ESPHome firmware still speaks OEM BLE (the stock QuietCool Smart Control app keeps pairing and controlling it), but its Upgrade command deliberately blocks QuietCool's firmware domains — so the Web-BLE flow above can't push the stock bin back over Bluetooth. This HTTP path reaches the device directly and isn't subject to that.

The mDNS name the device announces, OR its LAN IP. Auto-filled from the last successful flash on this browser.

Must start with http:// or https://. The hub fetches this URL over its own Wi-Fi — not through the device running this page.

Partition layout matters — only firmwares built for the OEM IT-AF-SMT layout will flash here (OTA slots at 0x20000 and 0x200000, 1.875 MB each). Safe to flash: the verified OEM V4.1 preset, this project's own builds (preserve the OEM layout via partitions.csv), and forks that ship the same partitions.csv. Stock ESPHome builds with the default 4 MB partition layout have different OTA addresses and slot sizes; they may refuse to write or fail to boot. Ordinary custom images keep app rollback, but the exact verified OEM restore is marked valid deliberately so it stays stock.

If supplied, the OTA aborts before writing if the downloaded bin's MD5 doesn't match — a cheap safety net against the wrong file landing in flash.

How does this work? / troubleshooting

The button issues a single POST http://<host>/api/flash_url?url=…&md5=… to the device. The device's http_flash_handler component validates the URL+MD5, returns 200 OK (body “Accepted…”) immediately, then ~500 ms later kicks off the ota.http_request OTA — pulls the bin, writes it to the inactive OTA slot, and reboots. Ordinary custom images retain normal app-rollback protection. The exact OEM V4.1 URL+MD5 preset instead marks stock VALID before reboot so it stays installed, erases only ESPHome's private NVS namespace, and preserves OEM pairings and settings.

No auth on this endpoint — matches the device's LAN-trust default (api/ota are also passwordless before Home Assistant adoption pushes per-device secrets). To lock it down, add auth: { username, password } under web_server: in your build.

Common failure modes:

  • "Network error" → device hostname doesn't resolve; try the LAN IP instead. The full mDNS name is required, including the MAC suffix (e.g. quietcool-atticfan-abcdef.local, not just quietcool-atticfan).
  • "404 Not Found" → device firmware doesn't have web_server + http_flash_handler wired. Re-flash with a current build that includes them.
  • 500 with a validation message (e.g. "Missing or empty 'url' parameter", "MD5 must be exactly 32 hex characters") → the device rejected the request; the reason is in the response body. ESPHome's IDF web backend surfaces the handler's validation errors as 500. The form pre-checks the URL and MD5, so you'll normally see the reason inline before anything is sent.
  • POST succeeds but device doesn't come back → check the device's UART/logger output. Ordinary custom images retain ESP-IDF rollback and should boot the previous firmware after a power-cycle. The verified OEM restore is deliberately marked valid so it stays stock; use UART recovery if that known image unexpectedly fails to boot.

Caveats

  • The OEM firmware does not verify signatures on OTA images — anything reachable at the firmware URL gets flashed. Only point this at images you trust.
  • If the hub has been paired with the QuietCool Smart Control app on Android or iOS, the factory test pair ID stops working — use the put it into pair mode option instead.
  • Wi-Fi password is transmitted in cleartext over BLE (an OEM trait, not ours). Acceptable for a one-shot bootstrap; BLE range is ~10 m.
  • If the host serving the firmware uses HTTPS, the hub trusts standard public CAs. If your cert isn't trusted, fall back to plain http://.
